Rozdział 1

🌐 Jak działa internet?

Kiedy wpisujesz adres strony w przeglądarce, tak naprawdę wysyłasz list do komputera gdzieś na świecie i czekasz na odpowiedź.

Wyobraź sobie restaurację. Ty (przeglądarka) siedzisz przy stoliku i zamawiasz jedzenie. Kelner (internet) zanosi zamówienie do kuchni (serwer). Kuchnia przygotowuje danie i odsyła z kelnerem. Ty otrzymujesz gotowe jedzenie (stronę HTML).

Kluczowe pojęcia

🖥️

Serwer

Komputer, który jest cały czas włączony i odpowiada na zapytania. Może obsłużyć tysiące użytkowników jednocześnie.

📬

HTTP / HTTPS

Język, którym rozmawiają przeglądarka i serwer. HTTPS to zaszyfrowana wersja — nikt po drodze nie może podsłuchać.

🏠

Adres IP / Domena

Każdy serwer ma adres IP (np. 142.250.74.46). Domena (google.com) to czytelna nazwa przypisana do tego adresu.

📦

Request / Response

Każda rozmowa w internecie to para: zapytanie (request) i odpowiedź (response). Przeglądarka pyta, serwer odpowiada.

Frontend — to co widzisz w przeglądarce

Pliki HTML, CSS i JavaScript, które przeglądarka pobiera raz i uruchamia lokalnie na Twoim komputerze. Odpowiadają za wygląd, animacje i interakcje.

🏗️

HTML

Struktura strony — nagłówki, przyciski, tabele, formularze. Szkielet budynku.

🎨

CSS

Wygląd — kolory, czcionki, rozmieszczenie elementów. Tynk i farba na szkielecie.

⚡

JavaScript

Logika i interakcje — reaguje na kliknięcia, wysyła zapytania do serwera, aktualizuje widok.

Popularne frameworki frontendowe: React Vue Angular Vanilla JS (bez frameworka)

Nasza apka używa czystego Vanilla JS — bez żadnego frameworka. Proste, szybkie, żadnych zależności.

Backend — silnik ukryty za kulisami

Działa na serwerze, użytkownik go nie widzi. Przyjmuje zapytania z frontendu, przetwarza logikę (np. sprawdza czy masz dostęp), komunikuje się z bazą danych i odsyła odpowiedź.

Rozdział 3

☁️ Gdzie uruchomić aplikację? Serwery i hosting

Twoja aplikacja musi gdzieś działać — na jakimś komputerze podłączonym do internetu 24 godziny na dobę, 7 dni w tygodniu. Masz kilka zupełnie różnych opcji pod względem ceny, wygody i kontroli.

To jak pytanie "gdzie mieszkać?". Możesz wynająć gotowe mieszkanie z meblami i mediami w pakiecie (PaaS) — płacisz więcej ale nic nie musisz robić. Możesz kupić pustą działkę i zbudować dom od podstaw (VPS) — tanie, ale sam kładziesz instalację elektryczną. Możesz też wynajmować biurko w coworkingu na godziny (Serverless) — płacisz tylko za czas w którym siedzisz.

1. Shared Hosting — najtańsza opcja dla stron

Twoja strona dzieli jeden serwer z setkami innych stron. Hostingodawca zarządza wszystkim — Ty tylko wrzucasz pliki przez panel WWW lub FTP. Nie masz żadnej kontroli nad serwerem.

Jak to działa: Logujesz się do panelu (cPanel, Plesk), wgrywasz pliki HTML/PHP, gotowe. Domena jest automatycznie podpięta.

✅

Plusy

Najtańszy hosting na rynku. Zero konfiguracji. Dobre do prostych stron i WordPressa. Wsparcie 24/7 od providera.

❌

Minusy

Nie można uruchomić Pythona/Node.js (tylko PHP). Zasoby CPU i RAM dzielone z sąsiadami — jeśli sąsiad dostanie dużo ruchu, Twoja strona zwalnia. Brak bazy danych PostgreSQL (tylko MySQL).

⚠️ Shared hosting nie nadaje się do naszej aplikacji — nie obsługuje FastAPI/Python ani PostgreSQL. Dobry tylko do prostych stron w HTML lub WordPress.

2. PaaS (Platform as a Service) — złoty środek ⭐

Wrzucasz kod na GitHub, platforma automatycznie go buduje i uruchamia. Nie musisz wiedzieć nic o konfiguracji serwerów, nginx, SSL czy aktualizacjach systemu. Platforma robi to za Ciebie.

Jak to działa: Łączysz repozytorium GitHub z platformą. Przy każdym git push platforma pobiera kod, instaluje zależności (pip install), i uruchamia aplikację. Automatycznie dostarcza certyfikat HTTPS.

🚂

Railway ★★★★☆ — używamy

Nowoczesny, bardzo wygodny. Jedno kliknięcie żeby dodać PostgreSQL, Redis czy inne serwisy. Przejrzyste ceny — płacisz za faktyczne zużycie zasobów (CPU, RAM). Darmowy tier: 5$ kredytu na start.

Typowy koszt: mała aplikacja to ~3–8$/mc

🎨

Render ★★★★☆

Bardzo podobny do Railway. Darmowy tier (ale aplikacja "zasypia" po 15 min bezczynności — pierwsze zapytanie czeka ~30s na "przebudzenie"). Wolniejsze wdrożenia niż Railway.

Typowy koszt: 0$ (darmowy z uśpieniem) lub 7$/mc (zawsze aktywny)

🛸

Fly.io ★★★★☆

Uruchamia aplikacje w kontenerach Docker w ponad 30 lokalizacjach na świecie — czyli serwer jest fizycznie blisko użytkownika. Bardziej techniczne niż Railway, ale bardzo elastyczne.

Typowy koszt: 0$ (małe aplikacje mieszczą się w darmowym tierze)

🟠

Heroku ★★★☆☆

Pionier PaaS, wymyślił tę kategorię. Przez lata był standardem dla startupów. W 2022 usunął darmowy tier i znacznie podrożał. Dziś mało kto wybiera go dla nowych projektów.

Typowy koszt: 5–25$/mc za podstawowy plan

Nasza apka działa na Railway. Każdy git push automatycznie wdraża nową wersję na produkcję w ciągu ~1 minuty.

3. VPS (Virtual Private Server) — pełna kontrola

Wynajmujesz wirtualny komputer z Linuxem, do którego masz pełny dostęp przez SSH (terminal). Możesz zainstalować cokolwiek, skonfigurować jak chcesz — ale wszystko musisz zrobić sam.

Jak to działa: Dostajesz adres IP i hasło root. Logujesz się przez terminal (ssh root@123.45.67.89), instalujesz Python, nginx (serwer WWW), konfigurujesz SSL (certyfikat HTTPS), uruchamiasz aplikację jako usługę systemową, ustawiasz firewall... To zajmuje kilka godzin pracy nawet dla kogoś z doświadczeniem.

🇩🇪

Hetzner ★★★★★

Niemcy. Najtańszy VPS na rynku — serwer z 2 CPU i 4GB RAM za 4–6€/mc. Świetna jakość sprzętu. Bardzo popularny w Europie. Cenowo bije konkurencję 2–3x.

🌊

DigitalOcean ★★★★☆

Droplet od 4$/mc (1 CPU, 512MB RAM). Świetna dokumentacja — mają tysiące tutoriali do każdego możliwego scenariusza. Mają też PaaS ("App Platform") jeśli nie chcesz konfigurować ręcznie.

🌐

Linode / Akamai ★★★★☆

Podobny do DigitalOcean. Od 5$/mc. Serwery w wielu lokalizacjach. Dobra alternatywa dla DigitalOcean.

🇫🇷

OVH / Scaleway ★★★☆☆

Francja. Tanie, ale interfejs i dokumentacja gorzej przetłumaczone. Popularne w Europie Zachodniej. Scaleway ma darmowy tier dla małych serwerów.

Co trzeba skonfigurować na VPS ręcznie:

  • System operacyjny (Ubuntu, Debian) — zwykle wybrany przy zakupie
  • Firewall (ufw) — blokuje niepożądane połączenia
  • nginx lub Caddy — serwer WWW który przekazuje ruch do aplikacji
  • Certbot — automatyczne certyfikaty HTTPS (Let's Encrypt, darmowe)
  • Systemd — uruchamia aplikację automatycznie po restarcie serwera
  • Aktualizacje systemu — regularnie, żeby łatać luki bezpieczeństwa
  • Monitoring — żeby wiedzieć gdy coś nie działa

4. Serverless — płacisz tylko za użycie

Zamiast serwera który cały czas działa, twój kod uruchamia się tylko w momencie zapytania i wyłącza się po chwili. Infrastruktura "znika" gdy nikt nie korzysta.

Taksówka vs samochód. VPS to samochód — płacisz ubezpieczenie i paliwo cały rok, nawet gdy stoi w garażu. Serverless to taksówka — płacisz tylko za kursy które rzeczywiście przejechałeś.
▲

Vercel ★★★★★

Numer 1 do hostowania frontendu (React, Next.js). Wdrożenie z GitHuba w 30 sekund. Darmowy tier bardzo hojny. Serverless Functions do prostego backendu. Nie nadaje się do długotrwałych procesów (max ~10s wykonania).

🔶

Cloudflare Workers

Kod działa na 300+ serwerach Cloudflare na całym świecie jednocześnie — dosłownie przy każdym użytkowniku. Błyskawiczne. Darmowy tier bardzo hojny. Ograniczenia: tylko JavaScript, max 128MB RAM, brak długich operacji.

🟠

AWS Lambda

Pionier serverless. Obsługuje Python, Node, Java i inne. Płacisz za milisekundy wykonania. Problem: "zimny start" — pierwsza funkcja po przerwie czeka 1–3 sekundy na "rozgrzanie".

📦

Netlify Functions

Połączenie hostingu statycznych stron z prostymi funkcjami backendowymi. Popularne wśród Jamstack developerów.

⚠️ Serverless nie nadaje się do naszej aplikacji — FastAPI to serwer który cały czas nasłuchuje, a PostgreSQL wymaga stałego połączenia. Serverless jest świetny do prostych funkcji i frontendów, nie do pełnych aplikacji webowych.

5. Managed Cloud — AWS, Google Cloud, Azure

Trzy gigantyczne platformy chmurowe które oferują setki różnych usług — od serwerów, przez bazy danych, przez AI, przez streaming wideo, aż po IoT. Są dla dużych firm i projektów wymagających ogromnej skalowalności.

🟠

AWS (Amazon Web Services)

Największy. 200+ usług. Używa go Amazon, Netflix, Spotify, NASA. Bardzo skomplikowany panel, certyfikacje trwają miesiącami. Drogi bez optymalizacji — słynne są przypadki gdy ktoś zostawił serwer włączony i dostał rachunek na 10 000$.

🔵

Google Cloud (GCP)

Mocny w AI i Big Data (BigQuery, Vertex AI). Sieć globalna Googla — najszybsza na świecie. Używa go Spotify, Twitter, GitLab. Lepsze narzędzia dla Data Science niż AWS.

🔷

Microsoft Azure

Dominuje w firmach które już używają produktów Microsoft (Office 365, Windows Server). Dobra integracja z Active Directory. Popularny w korporacjach i bankowości.

🤔

Kiedy używać?

Gdy masz setki tysięcy użytkowników. Gdy potrzebujesz globalnej skalowalności. Gdy masz zespół DevOps. Gdy compliance wymaga konkretnej infrastruktury. Nie na początek projektu.

Bonus: Co to jest Docker?

Docker to technologia konteneryzacji — pakujesz aplikację razem ze wszystkimi jej zależnościami (Python, biblioteki, konfiguracja) w jeden "kontener". Ten kontener działa identycznie na każdym komputerze i serwerze, niezależnie od systemu operacyjnego.

Docker to jak płyta CD z grą — zawiera wszystko co potrzebne do uruchomienia. Nie musisz instalować sterowników, sprawdzać wersji DirectX ani martwić się o system. Wkładasz płytę i działa. Kontener działa tak samo u Ciebie na laptopie jak na serwerze w centrum danych.

Większość platform PaaS i VPS uruchamia aplikacje jako kontenery Docker "pod spodem" — Railway, Fly.io, AWS i inne. Jako użytkownik Railway często tego nie widzisz, ale to właśnie kontener jest uruchamiany gdy wrzucasz kod.

🗄️ Bazy danych — gdzie mieszkają dane?

Baza danych to zorganizowane miejsce przechowywania informacji, do których możesz szybko dotrzeć, przeszukiwać i modyfikować. To nie jest zwykły plik — to wyspecjalizowany system zarządzający danymi.

Wyobraź sobie ogromny arkusz Excel, ale taki który może obsłużyć miliony wierszy jednocześnie, tysiące użytkowników piszących do niego w tym samym momencie, z gwarancją że żaden zapis nie zaginie nawet jeśli prąd wysiadnie.

Dwa główne typy baz danych

📊

SQL (relacyjne)

Dane w tabelach jak Excel. Tabele są ze sobą powiązane. Zapytania w języku SQL. PostgreSQL, MySQL, SQLite. Najlepsze do typowych aplikacji biznesowych.

📄

NoSQL (nierelacyjne)

Dane jako dokumenty JSON, klucz-wartość, grafy itp. Bardziej elastyczna struktura. MongoDB, Redis, Firebase Firestore. Dobre przy bardzo zmiennych danych lub ogromnej skali.

Jak SQL wygląda w praktyce?

Żeby pobrać wszystkie wydatki Adama z czerwca 2026, piszemy zapytanie:

SELECT sklep, suma, data
FROM wydatki
WHERE osoba = 'Adam'
  AND data >= '2026-06-01'
ORDER BY data DESC;
Nasza apka używa PostgreSQL na Railway. Dane przeżywają wszystkie restarty aplikacji bo PostgreSQL jest osobnym serwisem z własnym dyskiem (volume).

🔑 Autentykacja — jak apka wie kim jesteś?

Autentykacja to proces potwierdzenia tożsamości użytkownika. To nie to samo co autoryzacja (sprawdzenie czy masz prawo coś zrobić).

Autentykacja = pokazanie dowodu osobistego na wejściu do klubu (kim jesteś?). Autoryzacja = sprawdzenie czy masz bilet VIP do strefy za kulisami (co ci wolno?).

Rozdział 6

🔌 API — jak frontend rozmawia z backendem?

API (Application Programming Interface) to zestaw zasad komunikacji między dwoma programami. W przypadku aplikacji webowych, to lista adresów URL do których frontend może wysyłać zapytania.

API to menu w restauracji. Określa co możesz zamówić (jakie dane możesz pobrać lub wysłać), w jakiej formie zamawiasz (format JSON), i co dostaniesz w odpowiedzi. Kuchnia (backend) i kelner (API) obsługują tylko to co jest w menu.

REST API — najpopularniejszy styl

Każdy zasób (wydatek, konto) ma swój URL. Operacje wykonujesz metodami HTTP:

Metoda HTTPCo robiPrzykład w naszej apce
GETPobiera daneGET /api/wydatki — lista wszystkich wydatków
POSTTworzy nowy rekordPOST /api/wydatki — dodaj nowy wydatek
PUTAktualizuje cały rekordPUT /api/wydatki/42 — edytuj wydatek #42
PATCHAktualizuje część rekorduPATCH /api/wydatki/42/notatki — zmień tylko notatki
DELETEUsuwa rekordDELETE /api/wydatki/42 — usuń wydatek #42

Format JSON

Dane między frontendem i backendem są wymieniane w formacie JSON — to po prostu tekst w określonej strukturze, czytelny zarówno dla ludzi jak i maszyn.

{
  "sklep": "Biedronka",
  "suma": 47.50,
  "data": "2026-07-01",
  "osoba": "Adam",
  "pozycje": [
    { "nazwa": "Mleko", "cena": 3.99, "kategoria": "Jedzenie" }
  ]
}

Rozdział 8

💾 Backup — zabezpieczenie danych

Backup to kopia zapasowa danych przechowywana w innym miejscu niż oryginał. Jeśli coś pójdzie źle (awaria serwera, błąd ludzi, atak hakerski), możesz wrócić do stanu sprzed problemu.

Backup to ubezpieczenie. Nigdy nie masz nadziei go użyć, ale kiedy potrzebujesz — jest bezcenny. Warto robić go w innym fizycznym miejscu niż dane (dlatego nie trzymamy backupu na tym samym serwerze co baza).

Strategie backupu

📅

Pełny (Full)

Kopia wszystkich danych. Bezpieczna ale zajmuje dużo miejsca. Używamy tego — każdy backup to pełny snapshot.

➕

Przyrostowy (Incremental)

Tylko zmiany od ostatniego backupu. Oszczędność miejsca, ale przywrócenie wymaga wielu plików.

🔄

Różnicowy (Differential)

Zmiany od ostatniego pełnego backupu. Kompromis między pełnym a przyrostowym.

Nasza apka: GitHub Actions codziennie o 5:00 rano łączy się z PostgreSQL przez publiczny URL i eksportuje wszystkie dane (wydatki, konta, kategorie, wpływy) do pliku JSON. Plik trafia na GitHub — zupełnie inne miejsce niż Railway.

Zasada 3-2-1

Profesjonalny standard backupu: 3 kopie danych, na 2 różnych nośnikach, z czego 1 poza siedzibą (off-site). Nasza apka ma: dane na Railway + backup na GitHub — to 2 miejsca, co jest dobrym minimum dla prywatnego projektu.
